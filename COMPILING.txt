HOW TO COMPILE

Below is the basic procedure of setting up Common Lisp on Windows and running City of the Damned from source for those who have never tried Lisp before.

1. Create Lisp folders.

You need two:
- a general one, where you will keep all Lisp-related files, for example, C:\Lisp.
- a specific one, where you will keep your own Lisp projects (like CotD), for example, C:\Lisp\libraries.

2. Install SBCL

Download Steel Bank Common Lisp from www.sbcl.org. Install it somewhere to C:\Lisp\SBCL\<SBCL version>.

3. Set up Environmental Variables.

You need to create the following environmental variables for your user:
- HOME with the value C:\Lisp
- CL_SOURCE_REGISTRY with the value (:source-registry (:tree "C:/Lisp/libraries/") :inherit-configuration) 
- ASDF_OUTPUT_TRANSLATIONS with the value (:output-translations (T ("C:/Lisp/fasl-cache/" :implementation)) :inherit-configuration)

4. Install Quicklisp

Quicklisp is a packet manager for Common Lisp, which contains the most popular Lisp libraries.
Download the file https://beta.quicklisp.org/quicklisp.lisp, run sbcl.exe from cmd.exe and enter the following command in the SBCL prompt:
(load "C:/Lisp/quicklisp.lisp")

Quicklisp will respond with something like:

=== quicklisp quickstart 2015-01-28 loaded ===

   To continue with installation, evaluate: (quicklisp-quickstart:install)

So you need to enter in the SBCL prompt:
(quicklisp-quickstart:install)

Once Quicklisp finished downloading itself, you'll want to start it whenever you use SBCL. To do so, enter the following command in the SBCL prompt:
(ql:add-to-init-file)

5. Install Emacs

You'll want to install Emacs as you IDE. Download Emacs binaries for Windows (http://ftp.gnu.org/gnu/emacs/windows/) and install them to C:\Lisp\emacs.
You may also run addpm.exe to add Emacs to the Start menu.

6. Install and configure SLIME

Download SLIME that ensures connection from Emacs to SBCL from https://github.com/slime/slime/releases. Unpack SLIME to C:\Lisp\libraries\.
Create the file C:\Lisp\.emacs.d\init.el and put the following inside it:

(set-language-environment 'UTF-8)
(setq default-buffer-file-coding-system 'utf-8-unix)

(setq-default make-backup-files nil)

(setq-default auto-save-defaults t)

(setq-default indent-tabs-mode nil)

(setq w32-use-visible-system-caret t)
(cua-mode)

(show-paren-mode)

(setq inferior-lisp-program "C:/Lisp/SBCL/1.3.12/sbcl.exe")

(add-to-list 'load-path "C:/Lisp/libraries/slime-2.15")

(require 'slime)

(setq slime-net-coding-system 'utf-8-unix)

(slime-setup '(slime-repl
               slime-fuzzy
               slime-fancy-inspector
               slime-indentation))

(define-key slime-mode-map (kbd "TAB")
  'slime-indent-and-complete-symbol)
(define-key slime-mode-map (kbd "C-c TAB")
  'slime-complete-symbol)

(setq lisp-indent-function 'common-lisp-indent-function)

(define-common-lisp-style "my-indent-style"
  "My custom indent style."
  (:inherit "modern")
  (:variables
    (lisp-loop-indent-subclauses t))    
  (:indentation
    (if (4 2 2))
    (define (&lambda 2))
    (with-gensyms ((&whole 4 &rest 1) &body))
    (once-only (as with-gensyms))))

(setq common-lisp-style-default "my-indent-style")

(setq word-wrap nil)
(custom-set-variables
 ;; custom-set-variables was added by Custom.
 ;; If you edit it by hand, you could mess it up, so be careful.
 ;; Your init file should contain only one such instance.
 ;; If there is more than one, they won't work right.
 '(cua-mode t nil (cua-base))
 '(show-paren-mode t))
(custom-set-faces
 ;; custom-set-faces was added by Custom.
 ;; If you edit it by hand, you could mess it up, so be careful.
 ;; Your init file should contain only one such instance.
 ;; If there is more than one, they won't work right.
 '(default ((t (:family "Courier New" :foundry "outline" :slant normal :weight normal :height 90 :width normal)))))

 
The key strings here are:  
- (setq inferior-lisp-program "C:/Lisp/SBCL/1.3.12/sbcl.exe") which sets the path to you SBCL executable file. Change as appropriate.
- (add-to-list 'load-path "C:/Lisp/libraries/slime-2.15") which sets the path to SLIME. Change as appropriate.

7. Install dependencies

Download the SDL2 runtime library for Windows (SDL2-2.x.y-win32-x64.zip from https://github.com/libsdl-org/SDL/releases - any 2.0.5 or newer) and put SDL2.dll into C:\Lisp\SBCL\1.3.12. That library is all the SDL the game needs: there is no Lisp binding to install for it, since the game declares SDL2 to CFFI itself and opens it when it starts. It therefore has to be present to run the game, but not to compile or build it.
Start Emacs, press Alt + X (M x) and enter the word "slime" (without quotes) to run SLIME.
In the SLIME prompt enter the following command to load BORDEAUX-THREADS:
(ql:quickload "bordeaux-threads")
Enter the following command to load CFFI:
(ql:quickload "cffi")
Enter the following command to load DEFENUM:
(ql:quickload "defenum")
Enter the following command to load Cl-STORE
(ql:quickload "cl-store")
Enter the following command to load UIOP
(ql:quickload "uiop")
Enter the following command to load LOG4CL
(ql:quickload "log4cl")

8. Fetch CotD source files

Fetch CotD source files from GitHub (clone the repository) and put them to C:\Lisp\libraries.

9. Run CotD

In Lisp command prompt (SBCL or Emacs SLIME), enter the following commands one after another:
(asdf:oos 'asdf:load-op :cotd)
(cotd:cotd-main)

The first one loads the game to Lisp. The second one runs the game.


HOW TO BUILD A STANDALONE EXECUTABLE

The steps above run the game from a Lisp prompt. To instead produce a single executable that runs without SBCL or Emacs, use one of the build scripts in the repository root:

 - Windows:         build.bat
 - Linux and macOS: ./build.sh

Both do the same thing: change into src/, then run

sbcl --non-interactive --load ../build.lisp

build.lisp loads the cotd system and calls (cotd:make-exec). It is shared by both scripts so that the two cannot drift apart, and you can equally well run that one command by hand from src/.

All the Lisp libraries from the "Install dependencies" step above have to be installed first, since the build loads the whole system. SDL2 itself is not needed to build - the build never opens the library, only the finished game does - so a build machine does not have to have SDL2.dll or libSDL2 at all.

The executable loads the SDL2 library when it starts, so wherever the game is run, SDL2 has to be present: on Windows put SDL2.dll next to cotd.exe (when you hand the game to someone else, ship SDL2.dll with it); on Linux the system's SDL2 package (e.g. libsdl2-2.0-0 on Debian/Ubuntu) has to be installed.

If sbcl is not on PATH - the Emacs and SLIME setup above does not put it there, it only tells Emacs where SBCL lives - point the SBCL variable at it before running the script:

 Windows:         set "SBCL=C:\Lisp\SBCL\1.3.12\sbcl.exe"
 Linux and macOS: export SBCL=/usr/local/bin/sbcl

The executable is written into src/, alongside data/ and help/:

 - src/cotd.exe on Windows. It is built with :application-type :gui, so it opens no console window.
 - src/cotd on Linux and macOS.

Leave it there, or copy data/ and help/ along with it: a release build resolves its asset directory from the executable's own location rather than from the current directory, so it can be started from anywhere, but the data has to sit next to it. Saves, options.cfg, log.txt, highscores and morgue dumps are deliberately kept somewhere else - in the directory (uiop:xdg-data-home "cotd/") resolves to - so that an install into a read-only location still works.


CHECKING A BUILD

Started with no arguments, the executable goes straight into the game. It also takes three options, which answer and exit without opening a window or needing SDL2 - enough to check a build on a machine with no display:

 - cotd --version   prints the version (the one in cotd.asd).
 - cotd --check     prints where the executable looks for its data and whether the files it needs are there. Exit code 0 if the installation is complete, 1 if anything is missing - which is the quick way to catch a release archive packaged without its data/ and help/ directories.
 - cotd --selftest [dir]  proves the game actually runs: it opens its window, renders the main menu into it, presses the key that moves the menu selection, checks that the screen changed with it, and leaves through the quit path. Exit code 0 if all of that happened, 1 otherwise, with the reason printed. Given a directory, it writes the menu before and after the key press there as PPM files. Where there is no display at all it says so and runs the same check on SDL's dummy video driver instead of failing.
 - cotd --help      prints the above.

Anything else on the command line is ignored, so a launcher that passes arguments of its own cannot stop the game from starting.

On Windows cotd.exe is a GUI-subsystem program with no console attached, so this output goes nowhere when it is started from a prompt. Redirect it to see it:

cotd.exe --check > out.txt

The exit code is reliable on every platform either way.


NOTES FOR LINUX AND MACOS

The instructions above are written for Windows, but nothing in the game is Windows-specific. The shape is the same: install SBCL, install Quicklisp and run (ql:add-to-init-file), install SDL2 (e.g. "apt install libsdl2-2.0-0" on Debian/Ubuntu), put the repository somewhere ASDF can find it (~/common-lisp/ is searched by default), then (asdf:load-system :cotd) and (cotd:cotd-main).

Instead of the environment variables in step 3 ("Set up Environmental Variables"), the usual places for configuration are ~/.config/common-lisp/source-registry.conf for the source registry and ~/.sbclrc for the Quicklisp init.

macOS is UNTESTED. What follows is what to expect, not a verified recipe - if you get it working, corrections are welcome.

 - SBCL is available from www.sbcl.org or via "brew install sbcl".
 - Do NOT use "brew install sdl2". Homebrew's sdl2 is an alias for sdl2-compat, which is SDL2's API reimplemented on top of SDL3, and it does not behave identically: a synthetic SDL_TEXTINPUT event, which the headless event check pushes, faults inside SDL_PushEvent there. Install the real SDL2 instead - libsdl-org ships SDL2-2.x.y.dmg for macOS (https://github.com/libsdl-org/SDL/releases), containing a universal SDL2.framework. Copy that into /Library/Frameworks (or ~/Library/Frameworks), which is the first place the game looks. (cotd --selftest and the game's log both report which SDL is actually loaded, version and revision.) If you do end up on a Homebrew dylib, it lives under /opt/homebrew/lib on Apple silicon or /usr/local/lib on Intel, which may have to be added to cffi:*foreign-library-directories* or to DYLD_LIBRARY_PATH before CFFI will find it. The game's own library definition (in src/render.lisp) looks for the SDL2 framework first and then for libSDL2, in the REPL and in a release build alike.
 - On macOS a window and its event loop have to live on the process's main thread. The release executable runs the game on the main thread, so it should be fine. Running from SLIME is the catch: SLIME evaluates REPL input on a worker thread, so (cotd:cotd-main) typed there will fail to open the window. Start it on the main thread instead with (sb-thread:interrupt-thread (sb-thread:main-thread) #'cotd:cotd-main), or set swank:*communication-style* to :fd-handler or nil so that SLIME itself evaluates on the main thread. The level generator's worker threads never touch SDL.
 - build.sh itself is portable - plain bash, no GNU-only constructs - and writes src/cotd there the same way it does on Linux.
